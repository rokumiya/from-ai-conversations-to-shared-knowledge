# 対話から共有知へ

## AIを、人類の「共有知の入口」にする

> AIとの会話の中で、「これは消してしまうには惜しい」と思った部分だけを本人が選び、必要ならAIが会話の外でも読める形に整える。
>
> 本人が文章・名義・共有範囲を確認した後、その範囲の人が参照できる場所へ残し、後日、別の人とAIとの対話から出典付きで再発見できるようにする。

本稿は、特定の製品や保存形式の完成案ではなく、この入口の利用体験と基本原則を示す構想である。

目的は、本人が残したい知見を、元の対話の外で別の人が再発見し、利用できるようにすることである。一事業者のサービス内で利用者同士が共有する形でも、この目的は達成できる。公共Webへの公開は共有先を広げる選択肢であり、実現の前提条件でも、すべての仕組みが最終的に到達すべき形でもない。どの形態でも、本人による明示的な選択と、共有する文章・名義・共有範囲の確認を前提とする。

## 0. この提案の出発点：共有知への危惧と、消すには惜しい対話

この構想は、AI検索とWebの情報源について話していた私的な会話から生まれた。出発点には、二つの思いがある。

一つは、これから共有知が減っていくのではないか、という危惧である。

人が疑問を持ち、試し、解決した過程は、これまで掲示板、Q&A、ブログなどへ書かれ、後から別の人が参照できる情報になってきた。もし、そうしたやり取りがAIとの私的な対話だけで完結し、外へ残されなくなれば、新しい経験、訂正、発見が共有知へ加わる機会も減ってしまうのではないか。

これは、すでに共有知全体が減少していると断定するものではない。AIが既存の共有知を利用する一方で、新たな知見が他者へ届く経路が細れば、将来、人間とAIの双方が頼る知識の更新が弱まるのではないか、という懸念である。

もう一つは、その問題を話していた対話自体についての思いである。

> **そのまま会話を閉じて消すには惜しい。**

共有知の先行きへの危惧と、目の前の対話を残したいという実感が、この提案につながった。

話しているうちに、AIが公開Webの知識を利用するだけでなく、AIとの会話で生まれた新しい知識や発想を公共空間へ戻せないか、という考えへ進んだ。

その会話は、短いSNS投稿にするには長すぎた。論文でも、製品仕様でも、完成した事業計画でもなかった。

まだ構想の段階であり、実現方法も決まっていない。

それでも、その考えを会話の中だけで終わらせたくはなかった。

インターネットは、誰でも世界へ文章を公開できるようにした。

検索エンジンは、すでに公開された文章を誰でも見つけられるようにした。

対話AIは、そのさらに手前にある、まだ成果物になっていない人間の思考を、本人の意思で公共空間へ出す入口になれるかもしれない。

AIを、人間が作った知識を一方的に吸収する装置ではなく、これまで出会えなかった人々の経験や発想を、時間と場所を越えてつなぐ媒介にする。

この提案自体を、その最初の実例として公共空間へ残したい。

ただし、知見を次の人へ渡す仕組みまで、最初から公共Web全体に開かれている必要はない。一社のサービス内だけでは公共Webの情報源が細る懸念をすべて解消できなくても、私的な対話の中だけで終わるはずだった知見を、別の人が参照できる共有知として残せる。その実現にも意味がある。

## この提案は、一つの操作から始まる

AIとの会話に、次のような操作があったらどうだろう。

> **この部分を残す**

残すものは、大げさな知識でなくてよい。

- 半熟卵のトッピングに柚子胡椒を少し乗せるとおいしかった。
- ホットケーキメーカーには、意外とこんな使い道があった。
- この作業は、毎回ここで同じ無駄が発生している気がする。
- この道具は、ここだけ変えればもっと使いやすくなるのではないか。
- 試した方法はうまくいかなかったが、この条件だけは関係していそうだ。
- まだうまく説明できないが、こういう仕組みが必要なのではないか。

ここでいう共有知は、正しさが確認された知識だけを指さない。一行の生活上の工夫、個人的な経験、疑問、失敗、未検証の思いつきも含む。

今回の提案のように、短いSNS投稿にするには長すぎ、記事や企画書にするにはまだ固まっていない考えでもよい。

重要なのは、それが立派な成果物であることではない。

**本人が「これは残しておきたい」と思ったこと**である。

ここでいう「入口」には、二つの向きがある。

1. 私的な対話で生まれたものを、本人が共有知へ残す入口
2. 残されたものを、後日の別の人とAIが再発見する入口

単にAIから投稿できるようにするだけではない。時間も場所も異なる二つの対話を、共有知を介してつなぐことが目的である。

## 1. AIとの会話では、すでに多くのことが言葉になっている

人はAIとの会話で、質問に答えてもらうだけではない。

- 自分の状況を説明する。
- 昔の経験を思い出す。
- 何が不便なのかを言葉にする。
- 思いつきを試しに話してみる。
- AIの返答に反論する。
- 考えを少しずつ整理する。
- 試した結果を報告する。
- 最初にはなかった考えへたどり着く。

この過程では、これまでなら頭の中だけで終わっていたことが、すでに文章になっている。

しかし、会話が終わると、その大部分は社会的には消える。

会話履歴が個人のアカウントに残っていたとしても、他の人が検索し、引用し、関連する考えと結び付けられる共有知としては存在しない。

Xなどへ投稿すれば、短い一言でも公開されたURLを持ち、誰かが見つける可能性が生まれる。ブログに書けば、より長い考えも残せる。

だが、AIとの会話からあらためて投稿や記事を作るには、もう一度次のことをしなければならない。

- どこを取り出すか決める。
- 前後を知らない人にも分かるように書き直す。
- 投稿先を選ぶ。
- 長さや形式を合わせる。
- 個人的な文脈を削る。
- 公開してよい内容か確認する。

短い一言ならXへ書けばよいかもしれない。それでも実際には書かれないことが多い。

まして、まだ名前も付いていない複雑な考えは、短い投稿には収まらず、記事にするほど完成してもいない。その中間にあるものほど、出力先を持たないまま消えやすい。

この最後の壁を、AI自身が低くできるはずである。

## 2. 提案：「この部分を残す」

元の会話は非公開のままにする。

本人が選び、確認した文章だけを、本人が承認した範囲へ共有する。一事業者のサービス内でも、誰でもアクセスできるWeb上でもよい。

そのうえで、利用者が残したい箇所を選ぶか、AIへ次のように伝える。

> 今の話は残しておきたい。
>
> この部分だけ、次の誰かが見つけられるようにして。
>
> 個人的な事情は除いて、この考えを共有できる形にして。

AIは、選ばれた部分を会話の外でも読める形に整える。

短い内容なら、一言のままでよい。

複雑な内容なら、題名、短い要約、背景、考えたこと、まだ分からないことなどに整理してもよい。

利用者は、実際に共有される文章と名義に加え、誰が閲覧でき、どの範囲のAI回答で参照されるかを確認し、必要なら直す。そして「残す」と明示的に決めたときだけ共有される。公共Webへの公開とサービス内限定の共有は、確認画面で明確に区別する。

```text
[私的なAI対話]
        │
        │ 利用者が「ここを残す」と選ぶ
        ▼
[AIが会話の外でも読める形に整える]
        │
        │ 利用者が共有文・名義・共有範囲を確認する
        ▼
[共有知として残る]
        │
        ├─ 誰かが見つける
        ├─ 関連する考えにつながる
        ├─ 試した結果が加わる
        ├─ 反論や補足が加わる
        └─ 実現したものへつながる
        │
        ▼
[後日、別の人とAIとの対話]
        │
        └─ 「以前、こう残した人がいる」と出典付きで再発見される
```

AIが勝手に「価値がある」と判断して共有してはならない。

残すかどうかを決めるのは本人である。

## 3. 何を残してよいのか

原則として、本人が残したいと思い、その範囲へ共有する権利を持つものなら、種類を狭く限定しない。

| 例 | 残し方の例 |
|---|---|
| 小さな工夫 | 一言のメモとしてそのまま残す |
| おいしかった組み合わせ | 個人的な感想として残す |
| 意外な使い道 | 道具、使い方、注意点を添える |
| 日常や仕事で感じた無駄 | どこで何が起きているかを残す |
| 昔の経験や地域の記憶 | 時期や場所と、個人の記憶であることを添える |
| 疑問や違和感 | 結論を付けず、問いのまま残す |
| 未検証の発想 | 問題、思いついた案、分からない点を残す |
| 失敗した方法 | 何を試し、どうならなかったかを残す |
| 調査・検証結果 | 条件、手順、観測、推測を必要に応じて添える |
| 長く複雑な構想 | 要約と本文に分け、後から議論できる形にする |

これらに上下関係はない。

「再現できる技術情報」だけが共有知なのではない。誰かの生活上の工夫、現場で感じたこと、まだ形になっていない発想も、別の誰かにとっては出発点になり得る。

一方で、「残す」ことは、その内容が正しい、独創的である、重要であると保証することではない。

大切なのは、内容の性質を取り違えないことである。

- 実際に試したことなのか。
- 個人的に感じたことなのか。
- 人から聞いたことなのか。
- 推測なのか。
- 思いついた案なのか。
- まだ何も確かめていない問いなのか。

これは利用者へ毎回分類を入力させるという意味ではない。文章自体で分かる場合はそれでよく、必要ならAIが短いラベルを提案すればよい。

分類は共有のための試験ではなく、読む人に誤解させないための任意の補助である。

## 4. 雑に残せることを大切にする

この仕組みの入口を、論文投稿やデータ登録のようにしてはならない。

短い内容を残すために、何十個もの項目を入力させるなら、多くの人は何も残さないだろう。

最小の共有物は、次の程度でもよい。

```text
半熟卵に柚子胡椒をほんの少し乗せるとおいしかった。

— 匿名・2026-08-26・AIとの対話から
```

利用者が入力するのは本文だけでもよい。日時、選択済みの名義、AI対話から生まれたことなどは、システムが小さな付記として自動で添えられる。

技術的な検証なら、必要に応じて情報を増やせる。

```text
製品X v1.4では、条件Aのとき現象Yが2回起きた。
原因は設定Zかもしれないが、まだ確認していない。

種類: 観測と推測
環境: Windows 11 / 製品X v1.4
検証状態: 一人・一環境のみ
```

長い構想なら、さらに背景や未解決点を持たせられる。

つまり、すべての投稿へ同じ厳密な形式を要求するのではなく、内容に応じて段階的に構造を足せるようにする。

```text
短い共有メモ
    ↓ 必要なら
背景・分類・関連情報を追加
    ↓ 必要なら
検証・反論・改訂・派生を関連付ける
```

構造化は、残すための関門ではない。

後で見つけやすくし、誤解を減らし、別の知識とつなぐための追加機能である。

## 5. AIだからできること

検索エンジンは、すでに誰かが書いたものを見つけやすくした。

対話AIは、その一段手前にあるものを扱える。

**まだ公開文書になっていない人間の思考を、本人の意思で共有可能な形にする。**

AIはそのために、次の作業を手伝える。

- 会話から本人が選んだ部分を取り出す。
- 前後の会話を知らない人にも読めるようにする。
- 一言のメモ、短い投稿、長い構想など、内容に合う長さへ整える。
- 個人的な事情を落とした候補を作る。
- 観測、感想、推測、発想を混同しないように整理する。
- 類似する過去の投稿を探す。
- 別の言語へ翻訳する。
- 後から関連する経験、反論、実装を結び付ける。

後日の別の会話では、AIが単に検索結果を並べるのではなく、次のように人と人の思考をつなげられる。

> 似た考えを以前残した人がいます。まだ実装はされていませんが、その人は問題点をこのように整理しています。

ただし、AIがその考えの価値を決める必要はない。

多くの思いつきは、すでに存在するか、うまくいかない理由があるか、何の役にも立たないかもしれない。

それでも、ごく一部には、別の人の知識や技術と結び付くことで初めて価値を持つものがある。

発想した人が、文章を書く人、検証する人、実装する人、広める人のすべてを兼ねる必要はない。

本人が残したものを、未来の誰かが見つけ、価値を判断できればよい。

### 事業者と利用者の双方にとっての利点

この入口は、知見を人から人へつなぐとともに、サービスを提供する事業者と、それを使う利用者の双方に利点をもたらし得る。以下は期待できる仕組みと、導入によって確かめるべき仮説であり、効果を保証するものではない。

#### 知識を継続的に更新し、回答の質を高める

日々の対話には、新しい使い方、最近変わった条件、現場で試した結果、既存の説明への訂正などが現れる。そのうち本人が選び、共有を承認した部分を、日時や出典を持つ外部の記録として残せれば、サービスが参照できる知識を継続的に更新する経路になる。

たとえば、ある利用者が「最近の更新後は、この方法では動かなくなった」と残し、別の利用者が代わりの方法を試した結果を加える。後のAI回答は、古い説明だけでなく、条件の違いや訂正も出典付きで示せるようになる。

これは、会話全体を収集したり、モデルの再学習を待ったりすることを前提としない。承認された記録を検索・参照するだけでも、回答の新しさ、具体性、条件への適合性を高める可能性がある。

ただし、新しい投稿や多数の投稿が、そのまま正しい回答になるわけではない。未検証の経験を一般的な事実へ変えず、出典、日時、適用条件、訂正や反論を踏まえて提示する必要がある。雑に残せる入口を保つことと、回答で慎重に扱うことは両立できる。

#### 答えを受け取るだけでなく、発見を誰かへ渡せる

利用者にとっては、他の人の経験から助けを得られることに加え、自分の発見や工夫を次の誰かへ渡せること自体が、参加する理由になり得る。

掲示板やQ&Aで「自分の経験が誰かの助けになるかもしれない」と書き込む動機は、AIとの対話の中にも持ち込める。すでに話した内容から本人が選んだ部分を残せるなら、あらためて投稿を作る負担も小さくできる。

人は、反応が届かなくても発見を共有したいことがある。報酬、ランキング、リアクションの多さを参加の前提にする必要はない。貢献がどう使われたかの可視化は、第8節のとおり任意の付加機能でよい。

このような「助けてもらえるし、自分も何かを残せる」という体験は、そのサービスを選び、使い続ける動機になり得る。一事業者のサービス内での共有でも、別の利用者へ届くなら、その動機は成立し得る。

#### 知見と参加が相互に価値を高める

利用者が多様な経験を残し、それが別の利用者の回答や発見に役立ち、役立った利用者もまた経験を残す。この循環が成立すれば、参加者と有用な知見が増えることで、互いにサービスの価値を高めるネットワーク効果が期待できる。

事業者にとっては、モデル自体の性能に加えて、利用者が承認して共有した知見の蓄積、それを適切に見つけて回答へ結び付ける能力、安心して参加できる体験が、サービスの競争力につながり得る。利用者にとっても、同じ問題を一人で解き直す負担を減らし、自分にはなかった経験や発想に出会う機会を増やせる。

ただし、人数や投稿数が増えるだけでこの循環が成立するわけではない。検索の適切さ、訂正の反映、雑音への対処、本人の意思への信頼が必要である。一社内に蓄積された知見が、そのサービス独自の価値になることもあり得る。公共Webで共有された知見を用いても、発見・参照の質と利用体験によって価値を生み出せる。どちらの場合も、本人が承認した利用範囲を守ることが前提である。

## 6. 「学習に使う」と「共有知として残す」は違う

AIサービスには、会話をモデル改善に利用するかどうかの設定がある場合がある。

しかし、モデル改善への利用を許可することと、本人が選んだ考えを他の人が参照できる共有物として残すことは同じではない。

モデルへ取り込まれた情報は、一般に次のような形では扱えない。

- 誰が、いつ話したのか。
- 本人が何を、どの範囲へ共有したかったのか。
- 経験なのか、推測なのか、冗談なのか。
- 後から訂正されたのか。
- 誰かが試したのか。
- その知識が誰かの役に立ったのか。

ここで提案するのは、会話全体をモデルへ渡すことではない。

元の会話は非公開のままにし、その中から本人が選んだ部分だけを、独立して読める共有物として、本人が承認した範囲で参照できる場所へ残すことである。

モデルの重みに覚えさせるのではなく、出典を持つ外部の共有物として、人間とAIの双方が検索・参照できるようにする。

第11節のサービス内限定共有でも、この区別は変わらない。承認された範囲内で記録を検索・参照することと、モデル学習への利用は別であり、共有への承認を学習への同意へ読み替えてはならない。

### 誰の言葉や発想なのかを混同しない

共有物には、利用者自身が述べた内容、AIが読みやすく整理した内容、AIが新しく提案した内容、対話を通じて共同で形になった内容が混ざり得る。

本人が共有を承認したからといって、すべてを本人が単独で考えたことにしてはならない。必要に応じて「利用者自身の経験」「AIによる整理」「対話から形成」などを簡単に示せるようにする。

## 7. 残したものが育つ

共有した時点で、内容が完成している必要はない。

後から別の人が、次のような反応を加えられる。

- 自分も試したら、うまくいった。
- 自分には合わなかった。
- 別の使い方もある。
- 以前にも似た発想があった。
- この条件では成立しない。
- 実際に作ってみた。
- この発想から別のものを思いついた。
- 説明の一部が間違っている。

一つの正解へ統合しなくてもよい。

元の投稿を残したまま、補足、反論、改訂版、派生した考えを結び付けられればよい。

小さな一言は、そのまま一言として残り続けてもよい。複雑な考えだけが、時間をかけて育ってもよい。

---

## 8. できれば、残した人にも結果を返す

これは、本提案が成立するための必須条件ではない。

人は、報酬や反応を得るためだけに何かを外へ残すのではない。役に立つか分からなくても、本人が「残しておきたい」と思ったなら、それでよい。

まず必要なのは、私的な対話から、別の人が参照できる場所へ簡単に残せる出口である。

そのうえで、過度な追跡や複雑な仕組みを必要とせずに実現できるなら、残したものがその後どうなったかを本人へ返せるとよい。

- 誰かが関連する情報として見つけた。
- AIの回答で参照された。
- 誰かが試したと報告した。
- 反論や補足が付いた。
- 別の発想や実装へつながった。

自分の一言が、知らない誰かの役に立ったと後から分かることには、それ自体の喜びがある。

しかし、そのために入口の実装が難しくなり、仕組みそのものが実現しなくなるなら、結果を返す機能は後回しでよい。

---

## 9. 簡単に残せることと、安全であることを両立する

入口は簡単であるべきだが、AIが会話を自動共有してよいという意味ではない。

### 元の会話は非公開のままにする

共有するのは、利用者が選択し、共有文を確認した部分だけである。

### 共有される文章を先に見せる

「AIがうまく匿名化したはず」と信じさせるのではなく、他の人から実際に見える文章と情報を、共有前に本人へそのまま見せる。

### AIによる検査は補助に留める

AIは、次の可能性を警告できる。

- 氏名、住所、連絡先などの個人情報
- 会話に登場した第三者の情報
- 顧客、勤務先、共同研究などの秘密
- 著作物の過剰な転載
- 共有すると危険なセキュリティ情報
- 未公開の発明や、営業秘密として扱いたい情報

ただし、自動検査は完全ではない。最終的に共有するかを決めるのは本人である。

### 共有後の限界を伝える

共有後に非表示や撤回ができても、すでに他者が保存、引用、複製した内容を完全には回収できない。そのことを共有前に分かりやすく示す必要がある。

### 共有範囲を確かめ、名義を選べるようにする

共有先は、一事業者のサービス内でも公共Webでもよい。自分だけの保存は、別の人へ知見をつなぐ共有とは区別する。

限定共有でも、文章・名義・閲覧できる人とAI回答での参照範囲を共有前に確認する。共有範囲は短く分かりやすく示し、毎回複雑なアクセス設定を要求しない。後から公共Webへ公開するなど範囲を広げる場合は、改めて本人の明示的な承認を得る。撤回の限界の説明も、限定共有だから省いてよいわけではない。

一方で、誰の名義で残すかは本人が選べるようにする。実名、仮名、匿名のいずれでもよい。

毎回の操作を重くしないため、よく使う名義を既定値にし、必要なときだけ変更できる設計が望ましい。

---

## 10. この提案が目指さないもの

- すべてのAI会話を保存・共有すること
- AIが自動的に「価値ある考え」を選ぶこと
- 投稿された内容をすべて正しい知識として扱うこと
- すべての投稿へ学術論文のような証拠を要求すること
- 短い投稿を複雑なデータ入力へ変えること
- ブログ、SNS、Wiki、Q&A、論文を置き換えること
- モデル学習への同意と、共有知として残すことへの同意を同一視すること
- 技術情報だけを対象にすること

この仕組みは、既存の公開手段を使うほどには完成していない思考にも、小さな出口を作るものである。

---

## 11. もし最初に試すなら

最初から世界規模の知識基盤を作る必要はない。

### 一事業者のサービス内だけでも成立する

誰でもアクセスできる公共Web上で、公開、検索、運営、訂正などを広く機能させるには、長い道筋が必要になるかもしれない。その実現を待つことを、共有知を残す仕組みの開始条件にする必要はない。

まず、一事業者が提供するサービスの利用者同士で、本人が承認した知見を共有する形でもよい。ここでいう「一社内」は、従業員だけの社内情報共有ではなく、その事業者のサービスを使う別の利用者へ知見が届くことを指す。

既存の対話画面、アカウント、検索機能などを活用できれば、小さな規模で選択・整形・確認・共有・再発見の流れを試しやすい。元の会話を他の利用者へ開かず、承認された共有物だけを対象にできる。

これは公共Web公開へ進むためだけの暫定形ではない。一社のサービス内に留まっても、ある人が残した経験を別の人が見つけ、使えるなら、共有知を残すという目的は達成される。一社による運営や、そのサービス内だけでの知見の蓄積・提供も、本提案から一律に排除しない。

公共Webへの公開や、他のサービスとの連携は、必要に応じて選べる拡張でよい。実施する場合も、利用者が承認した範囲を自動で広げず、公開される内容と範囲について改めて確認を得る。利用者に多数の設定を要求するのではなく、まず「このサービスの利用者に共有する」など、実際の範囲を短く示して確認できればよい。

最初に確かめるべきなのは、技術ではなく、次の一点である。

> AIとの会話に「この部分を残す」という出口があれば、人は、今までなら消していたものを本当に残すだろうか。

### 最小の試作例

1. 利用者が会話の一部を選ぶか、「今の話を残したい」と伝える。
2. AIが、会話の外でも読める文章を作る。
3. 利用者が共有される文章・名義・共有範囲を確認し、明示的に承認する。
4. 承認された範囲の人が読める簡単なページへ保存する。
5. 各投稿にURLと日時を付け、その範囲内で全文検索できるようにする。
6. 同じ共有範囲の別の利用者のAI対話から関連する投稿を見つけ、出典付きで提示する。

限定共有では、ページだけでなく検索結果やAI回答でも共有範囲を守る。公共Webへの公開を選ぶ場合は、誰でも参照できる形にすればよい。

保存形式は、最初はMarkdownや単純なJSONでもよい。利用者にYAMLやスキーマを意識させる必要はない。

### 試作で扱う例

技術的な検証だけで試すと、この構想を再び狭く理解してしまう。

少なくとも次のように異なる例を使う。

- 一行の食べ方や生活上の工夫
- 道具の意外な使い方
- 個人的な経験や記憶
- 日常や職場で感じた問題
- 未検証のアイデア
- 失敗した試み
- 条件付きの技術情報
- 今回のような長い構想

### 成功を判断する問い

- 残すまでの操作は十分に軽いか。
- 本人が意図した内容と、共有文が一致しているか。
- 誰が閲覧でき、どの範囲のAI回答で参照されるかを、本人が理解して承認できるか。
- 元の会話を知らない人にも意味が通じるか。
- 「この機能がなければ残さなかった」と言える投稿が生まれるか。
- 個人情報や秘密を共有前に見つけられるか。
- 後から誰かが検索し、利用し、関連付けられるか。
- 別のAI対話で、関連する投稿を自然に再発見できるか。
- 結果の通知がなくても、投稿者がまた何かを残したいと思えるか。
- 共有物を参照しない場合と比べて、回答の新しさや具体性が増し、誤りや古い情報への依存を減らせるか。
- 新しい投稿や訂正が、共有範囲を守って後の検索・回答へ反映されるか。
- 発見を残せることが、そのサービスを選び、使い続ける理由になるか。

## 12. 実現の参考になる既存の仕組み

この構想を実現するために、一からすべてを作る必要はない。

短文投稿、ブログ、ノートサービス、Wiki、Q&A、会話共有、データ寄付、知識グラフなど、近い役割を持つものはすでにある。

AIとの会話から知識を共有するうえで参考になる例も存在する。たとえば、次の二つは本提案と重要な部分で重なる。

- [**Stack Overflow for Agents**](https://stackoverflow.blog/2026/06/10/announcing-stack-overflow-for-agents/) は、ソフトウェア開発中にエージェントが得た知見を起草し、人間が確認して公開し、他者が検証する仕組みを提供している。
- [**The Foundation**](https://github.com/dannwaneri/chat-knowledge) は、AI会話を取得し、知見を抽出し、非公開から公開へ切り替えて連合できる実装である。

このほかにも、SNS、注釈、知識管理、来歴記録など、実現の参考にできる仕組みは多い。

ここで重視しているのは、特定分野向けの投稿システムや、会話全体の共有ではない。

**一般の人が、私的なAI対話の中から、一言の工夫でも長い未完成の構想でも、本人の判断で「ここだけ残す」ことのできる、日常的な出口**である。

既存の取り組みから、公開までの流れ、検証、検索、来歴の残し方などを学び、使えるものを組み合わせながら、この日常的な出口を形にできる。

## 13. 未解決の問い

- 共有知を置く場所は、誰が運営するのか。
- 一社で運営する場合、共有物の利用条件や、サービス終了時の扱いをどう定めるか。
- 必要になった場合、共有物の持ち出しや公共Webへの公開、他サービスとの連携をどう実現するか。
- 雑な投稿を許しながら、スパム、宣伝、嫌がらせをどう抑えるか。
- 「価値を事前審査しないこと」と「発見可能な品質」をどう両立するか。
- 類似した投稿を、削除せずにどうまとめるか。
- 個人的な経験と、他者についての危険な断定をどう区別するか。
- 共有後の訂正、撤回、削除要求をどう扱うか。
- 著作権、ライセンス、発明、営業秘密をどう分かりやすく確認するか。
- AIによる要約が、本人の意味を変えていないことをどう確かめるか。
- 一行のメモと長い構想を、同じ場所でどう発見しやすくするか。
- 間違い、既出案、役に立たない投稿を含む雑多さを、共有知の性質としてどこまで受け入れるか。

これらは重要だが、最初の操作を複雑にする理由にはしない。

入口は簡単にし、必要な安全性、履歴、検証、運営をその後ろに設計する。
